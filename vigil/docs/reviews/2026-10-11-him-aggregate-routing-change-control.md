# HIM 1.1.0 Aggregate Harm route-first screening — controlled change

**Date:** 11 October 2026  
**Branch:** `agent/incident-ecosystem-ingestion`  
**Human authorisation:** The maintainer explicitly approved replacing source-format-driven Aggregate Harm selection with mandatory screening of deployed potentially generalisable mechanisms, and requested bounded implementation on the active working branch.  
**Scope:** Methodology, schema text contract, optional structured-screen validator checks, regression tests and adjudication workflow. No automatic Incident/HIM re-adjudication, population inference or website change.

## MAINTAINERS Gate 1 — control-change disclosure

1. **Current behaviour.** HIM 1.1.0 selects an exclusive `specific_consequence` or `generic_deployed_evaluation` pathway. Generic routing descriptions privilege benchmarks/watchdogs/product-wide studies; the validator verifies the chosen pathway's format, assessed-row evidence and band-local denominator but cannot determine if a specifically selected route is appropriate. Source format can therefore suppress Aggregate Harm screening.
2. **Proposed behaviour.** Every newly created or substantively reopened HIM 1.1.0 assessment must screen actual deployment, potentially generalisable eligible-domain mechanism and whether an actual bounded harmed case is being assessed. The combination deployed=true / mechanism=true / actual bounded harm=false **requires `generic_deployed_evaluation`** regardless of whether the evidence was obtained by a user screenshot or watchdog test. Evidence needed to **score** (reproducibility/strong corroboration, relevant feature-specific denominator, credible aggregate consequence, safeguards) remains independently required. Insufficient scoring evidence means generic-route **SU**. A genuinely specific harmed case retains `specific_consequence`, with no reach multiplier.
3. **Pass/fail delta.** Once an `aggregate_harm_screening` object is supplied, a record with the three positive-screen conditions and `specific_consequence` newly fails. The same screened record with `generic_deployed_evaluation` and an evidence-bounded SU passes. Records declaring an inconsistent or ungrounded screen fail. Historical valid unscreened records continue to pass; no blanket schema migration is imposed.
4. **Affected surfaces.** `vigil/methodologies/VIGIL.HarmImpactMatrix.v1.1.0.json`, `vigil/VIGIL.Schema.json`, `vigil/scripts/validate-vigil-records.py`, `vigil/tests/test_validate_vigil_record_rules.py`, `vigil/docs/incident-severity-standard.md`, `vigil/docs/maintenance/INCIDENT-ADJUDICATION-WORKFLOW.md`. Stage 02 Harm Impact labels may later need projection updates when a case is separately and explicitly re-adjudicated; none are changed here.
5. **Expected corpus impact.** INC-012 is a confirmed route-review candidate and INC-192 (generic SU), INC-103 (specific relational S4) are comparison cases. Exact historical candidate count has **not been measured**. This patch does not alter historical valid-record acceptance merely because they lack the new structured screen.
6. **Repair implications.** Newly screened records must document their source-backed gate decisions. Existing cases require individual source-first review before pathway, HIM band, taxonomy, provenance or narrative changes; no bulk rewrite/regex migration and no assumption that 117 million general users is the relevant relational cohort.
7. **Data loss / drift risk.** Risk of treating one live screenshot as proof of platform prevalence, S5, injured users, or an actual provider objective; risk of losing actual injured-person consequences through an overzealous generic route. Both prohibited. Also risk of CI damage from retroactive mandatory fields; this change preserves legacy structural acceptance.
8. **Appropriate enforcement.** The methodology controls routing meaning; schema names and fields provide the controlled contract; validator enforces Boolean gate consistency and provenance once structured screening is declared. Independent judgement and source examination are required to determine the truth of the three booleans; neither regex nor the website renderer can establish factual deployment, generalisability or bounded materialised harm.
9. **Stop condition.** After implementation, validate the control read-only against existing records, examine CI and report any failures. Do not modify historical Incident records or perform multi-record remediation without a separate human Gate 2 decision.

## Evidence and adjudication boundary

- INC-012: source is a preserved user-posted SuperGrok output expressing dependency strategy; the *reporting format* is not a documented individual relational injury. Under the new screening rule, its existing `specific_consequence` route must be reconsidered. Nothing in this change proves the strategy was product-wide, reproducible, or encountered by 117 million relevant eligible users.
- INC-192: independently conducted live-product evaluation already uses `generic_deployed_evaluation` with SU because scored cohort and consequence remain insufficient.
- INC-103: reported particular relational consequences remain a `specific_consequence` case and must not inherit platform-wide reach.
- The underlying five Aggregate Harm domain gates, evidence thresholds, S1–S5/SU meanings and maximum-dimension derivation are **unchanged**.

## Concurrency and Gate 2 hold

Edits are isolated to the governing methodology, schema, validator, tests and guidance. Each GitHub write uses the latest blob SHA so contemporaneous changes to the same file reject stale overwrites. No canonical Incident, published Case File, generated index or taxonomy class is modified. The optional structured screen is a compatibility provision, not a finding that every historical case is already compliant with the new analytical routing policy. Historical routing census and any affected-record correction require separate controlled review.
