# Proposed methodology and semantic QA changes

Recommendations only. This audit implements none of these in production.

## Mechanically checkable proposals

1. Require a stable Incident/episode/clause identity, source pointer and pinned taxonomy edition for every disposition. Detect duplicate or orphan IDs and legacy status aliases. Distinguish current review state from historical snapshots.
2. Require separately populated materiality, taxonomy coverage, operative exclusion, gap diagnosis, evidence limitation and actor/system fields. Validate types, not only nonempty lengths: the audit's batch041 layout error demonstrates why a string must not pass as a list of class tests.
3. Require each referenced class to resolve to the applicable published contract; validate literal recognition/exclusion versions or hashes. Check that the packet includes a reasoned polarity assessment and does not contradict its own declared recommendation structurally.
4. Require one primary recommendation from the controlled list, with missing-evidence facts for an evidence finding and a consolidated mechanism reference for any gap candidate. An unresolved fact is not the same as an unperformed review; use different completion fields.
5. Preserve an immutable prior-decision reference and an explicit supersession/correction link. Generate population partitions and register indexes from stable identities. Keep historical packets, current register and canonical data distinct.
6. Flag empty source references, inaccessible-link claims represented as direct inspection, unversioned control obligations, unsupported actor identity, generic copied rationales and repeated unclassified mechanism phrases for review. These are flags, not automatic substantive verdicts.

## Substantive human or model-assisted adjudication

1. **Materiality before fit.** State the occurrence-specific governance proposition without a class name. Establish what happened, who acted, what was observable and why it matters. Only then compare current classes. A class rejection cannot answer the independent materiality question.
2. **Explicit gap diagnosis.** For material unmatched propositions choose existing-class fit, evidence gap, boundary/terminology repair, decomposition/family question, contextual support or genuinely missing concept. Test the nearest classes' entire conditions and exclusions; explain why narrower clarification would or would not suffice.
3. **Review both polarities.** Inspect actual refusals, stops, holds, corrections, independent checks, signal delivery and containment. A successful bounded control can coexist with earlier failure and remaining independent harm. Announcements, intended controls and absence of harm alone are insufficient.
4. **Distinguish evidence axes.** Record unknown occurrence separately from unknown internal cause, actor or precise locus. Do not demand hidden telemetry when output/action evidence suffices for the class. Do not manufacture implementation, intent, vulnerability or a duty from harm.
5. **Scope the system and interval.** Separate model, delegate, provider, external defender, human actor and affected service. Distinguish source-supplied pseudo-history from observed execution. Compare task/control scope, intervention timing and actual effect. Keep legitimate independent context when no assessed-system property is established.
6. **Test claims against actual obligations.** Identify a service promise, required check, protected-information boundary or duty at the relevant time. A starting default is not a lock; a notification request is not receipt; an actual revocation is not proof of repaired custody; preserved archives are not usable restores.
7. **Return to original sources for coverage.** Compare segmentation with surrounding source episodes. Record omitted propositions separately from the frozen disposition denominator; check whether another Incident already represents them. Do not confuse all listed clauses accounted for with every source proposition captured.
8. **Cluster across the corpus.** Periodically compare retained material clauses and evidence-limited cases by mechanism, including successes and failure counterexamples. Review shared occurrence identity: several records about the same evaluator misconfiguration are not independent recurrence. Treat semantic similarity as a discovery aid, never as a mapping rule.
9. **Challenge generic exclusions.** Review phrases such as no later misuse, only remediation, no model intent, no internal logs, planned safeguard and human-only aftermath against the actual occurrence. They can identify valid limits or hide unsupported closure; none is a universal verdict.
10. **Independent assurance.** Before using audit results as research evidence, have a human adjudicate all proposed class/gap changes and a stratified sample of retained and evidence-limited cases. Include disagreement records and source access limitations. Estimate inter-reviewer agreement or taxonomy recall only with an appropriate independent design; schema validation and this audit's counts cannot supply those measures.

## Concrete prospective review examples

| Trigger | Required review | Invalid shortcut |
|---|---|---|
| A protected push is rejected, then an existing route is exploited | Preserve bounded rejection success and later route failure separately | All controls failed because an eventual bypass occurred |
| A factual draft drops a material risk fact, source recording intact | Examine representation fidelity and FC027/011 boundary, then final reliance separately | No verified reliance, therefore immaterial |
| A control is available only as a policy announcement | Retain material design/response context; seek actual operation before effectiveness success | Named safeguard means success |
| A service is suspended for security | Check actual continuity obligation, permitted restriction and feasible safe response | Security purpose proves every continuity requirement met |
| A message reports a delegate removed a monitor and parent accepts it | Review accepted evidence/authority reasoning; distinguish later user-facing denial | Signal-delivery failure despite actual receipt |
| Full issue source contains a stop-everything/remote-merge allegation, segmented clauses cover only bedtime | Record the omitted proposition and check corpus duplicates | Every listed clause has a status, therefore the source is fully covered |

Implementation should be a separately reviewed proposal under existing repository gates. It must not convert these checks into automated class assignment, retrospective boilerplate notes, automatic legal duties or new permanent review-storage requirements.
