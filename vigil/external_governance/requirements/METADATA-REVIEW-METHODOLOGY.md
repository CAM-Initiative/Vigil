# External Requirement Metadata Review Methodology

## Purpose

The external-requirements corpus must distinguish between:

1. metadata that was reviewed against the source and populated;
2. metadata that was reviewed and is not specified by the source;
3. metadata that was reviewed and is not applicable to the represented proposition; and
4. metadata that has not yet received a source-fidelity decision.

An empty array in a canonical source/version requirement shard does not, by itself, establish which of those states applies.

The companion `metadata-review.json` ledger records that decision state without rewriting legacy requirement records merely to manufacture completeness.

`reextraction-backlog.json` separately records records whose source-level meaning cannot be made faithful by field population alone. Fields materially affected by a queued fidelity defect remain `review-required` until the record is enriched or deterministically migrated.

## Fidelity-critical fields

The following fields require explicit review-state tracking:

- `applicable_actor`
- `governed_object`
- `timing_or_frequency`
- `required_artefacts`
- `evidence_expectation`
- `verification_method`
- `applicability_conditions`
- `exceptions_or_qualifications`

The first two are structurally mandatory and non-empty under the canonical EXTREQ schema, but they still require substantive source review before they can be treated as fidelity-assured.

## Review states

### `populated-reviewed`

The field contains one or more values and those values have been substantively checked against the identified source proposition.

### `not-specified-by-source`

The field has been reviewed against the source and the source does not specify that semantic dimension for the represented proposition.

Use this where a dimension could conceptually apply, but the source is silent. For example, a requirement may impose a duty without prescribing a frequency.

### `not-applicable`

The field has been reviewed and the semantic dimension does not apply to the proposition.

Use this sparingly. For example, a definitional provision may not have a required artefact or verification method because those concepts do not form part of the proposition.

### `review-required`

No defensible source-fidelity decision has yet been recorded for that field.

This is the default state for legacy records that have not been re-reviewed under this methodology.

## Consistency rules

- `populated-reviewed` requires the corresponding canonical field to contain at least one value.
- `not-specified-by-source` requires the corresponding field to be empty.
- `not-applicable` requires the corresponding field to be empty.
- `review-required` may accompany either an empty or populated field. Existing content is not treated as source-assured merely because it is present.
- A field must not be populated with inferred audit evidence merely because that evidence would be useful. The metadata must remain source-faithful.
- `required_artefacts` describes outputs, documents, records or other artefacts required by the source proposition.
- `evidence_expectation` describes evidence expressly required or necessarily generated by the source proposition; it is not a generic audit wish-list.
- `verification_method` describes a source-specified assessment, testing, review or verification method. It must not be invented from good practice.

## Review queue

`validate-external-requirement-metadata.py` produces a review queue from canonical requirements and staged semantic re-extractions.

Missing ledger entries and `review-required` field states are review work, not silent success.

The validator has two modes:

- default mode reports unresolved review work but fails only on contradictory or malformed review-state contracts;
- `--strict` also fails while any fidelity-critical field remains `review-required` or lacks a ledger decision.

This allows the historical corpus to remain processable while new and repaired records can be held to a progressively stricter contract.

## Completion rule

A requirement is `metadata-complete` only when all eight fidelity-critical fields have explicit non-`review-required` decisions and all decisions are consistent with the canonical field values.

Metadata completeness does not, by itself, establish substantive legal interpretation correctness or human verification of the requirement.

A source may therefore be fully metadata-reviewed while still carrying a source-fidelity or re-extraction qualification. Metadata completion and clause-extraction completion are separate claims.
